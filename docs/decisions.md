# Decisions

## Principles

P-deterministic-guards-over-prose: when a loop or skill must be constrained, prefer a check it cannot argue with over an instruction
  promoted 2026-09-17 - recurred in D-dream-constraints, D-deploy-floor, D-verification (factory-dream-loop/spec.md); matches CLAUDE.md "prefer a deterministic check it loops against"

P-unattended-host-is-codex: unattended sessions run on Codex; Claude is the interactive host
  promoted 2026-09-17 - recurred in D-dream-agent, D-labeller (factory-dream-loop/spec.md) and the foreman design (memory prefers-llm-autonomy-over-guardrails)

## Factory policy

D-policy-surface: What does the loop edit? (2026-09-17, factory-dream-loop/spec.md)
  ✓ `factory/skills/foreman/SKILL.md` prose only - it is the one input the foreman reads on every cold turn (`start_prompt` in `foreman.py`), it is under 150 lines, and it changes nothing the runner enforces ⚠ replaying a prose policy costs one paid model call per decision point, unlike the paper's free code replay
  ✗ `enforce`, caps, hard stops, `model.decide()` - the runner alone enforces hard stops and caps (CLAUDE.md); a loop that edits its own guardrails has no guardrails
  ✗ `factory/references/factory-run.md` - stage skills read it too; editing it moves stage behavior, which the loop cannot score
  ✗ config knobs (`foreman_model`, `foreman_effort`) - a model or effort change cannot be replayed on recorded turns, since the recorded decision was made by the old model

D-first-slice: Which part of "the whole system should learn to self-operate" is built first? (2026-09-17, factory-dream-loop/spec.md)
  ✓ the foreman policy loop plus a harness-fault feed - the foreman's turns are the only decisions the factory records one by one with their outcomes (`foreman/turns/{n}/decision.json`, `factory.foreman-turn/1`), so only they can be scored offline; the fault feed costs nothing extra because the labeller already reads whole runs, and the recorded history shows about half the bad turns were runner crashes or malformed records the foreman cannot fix (gcp-costs run: two overrides of `AttributeError: provided_by_runner`; three runs with malformed-decision fallbacks: `decision.effort: not allowed on action 'repair'` in `1038` ship-1 turn 3 and `1144` build-1 turn 3, `decision.resolve_conditions: not allowed on action 'park'` in `1322-2` ship-3 turn 10) - auto-applied at Confidence: 80%, user chose "best potential long term" (user, 2026-09-17)
  ✗ foreman loop only - teaches the policy to route around harness bugs that a person should fix instead
  ✗ whole-system loop including build and ship skill text - a stage skill's outcome is only observable by running the stage again, which costs 5 to 50 minutes and 2 to 30 million tokens per attempt; the paper keeps the underlying agents fixed for the same reason

D-observation-builders: Should the loop also edit what the foreman sees (`digest()`, `event_message()`)? (2026-09-17, factory-dream-loop/spec.md)
  ✗ yes, in this slice - it would make the world format store raw sources instead of digests and double the replay surface
  ⊘ not doing - the builders are deterministic runner code and stay hand-edited; reopen when a dream round's report shows replay agreement stuck below 0.9 for two consecutive rounds with the labeller notes blaming truncated or missing observations

D-deterministic-prepolicy: Should a deterministic rule layer answer easy events before the LLM, so replay is free for those? (2026-09-17, factory-dream-loop/spec.md)
  ✗ yes - Tobrun chose full LLM authority over deterministic rules for the foreman (user, 2026-09-17, memory `prefers-llm-autonomy-over-guardrails`)
  ⊘ not doing - reopen when two dream rounds in a row propose a rule that is a pure function of the gate code and the same-failure streak

D-deploy: How does an accepted revision reach production? (2026-09-17, factory-dream-loop/spec.md)
  ✓ commit and push: the dream command writes the revised skill, rebuilds `plugins/`, runs `scripts/validate.sh`, commits to `main` with the score table in the commit body, and pushes to `origin` - the runner resolves skills to the generated tree in this checkout whenever the installed Codex plugin differs from it (`skill_bundles` in `provenance.py`, `resolution: direct-path`), which is how every run resolves whenever the installed plugin differs (`runtime.json`, 2026-09-18; 38 of 82 attempt records still show `installed-plugin`, and the fallback engages on the next cold turn after a deploy), so the commit is the deployment for new turns (user, 2026-09-17) ⚠ no person reads the revision before it governs runs; every later turn record carries the policy hash so a regression is attributable and `git revert` rolls it back ⚠ a run in flight reads the new file on its next cold turn; the deploy prints `codex plugin add factory@nurbot` as the way to make the installed plugin match again
  ✗ open a pull request - the user wants the loop closed without a reader
  ✗ candidate file only - never closes the loop

D-deploy-floor: How much history must exist before a revision may deploy on its own? (2026-09-17, factory-dream-loop/spec.md)
  ✓ 6 worlds and 2 repositories: at least 6 worlds in the confirmation set spanning at least 2 repositories by remote URL - below the floor a dream round still runs, writes its report and candidate, and deploys nothing (user, 2026-09-17) ⚠ if the factory keeps running on one remote the floor never clears and deployment stays manual ⚠ with fewer worlds than the floor plus a non-empty selection set (today's six-world corpus), the confirmation floor cannot clear and every round is report-only until the corpus grows; the 7e e2e asserts exactly this
  ✗ no floor - the first revision would deploy from four foreman runs of one repository's test tooling
  ✗ 6 worlds from any repositories - accepts a first revision tuned to one repository's failure families

D-canary-deploy: Should a new revision first run in shadow mode next to the incumbent on live runs? (2026-09-17, factory-dream-loop/spec.md)
  ✗ yes, now - needs two foreman sessions per event and a comparison the runner does not have
  ⊘ not doing - reopen when a deployed revision is reverted after a live regression, which `factory report --by-policy` would show

## Factory history

D-world-unit: What is one replay world? (2026-09-17, factory-dream-loop/spec.md)
  ✓ one run per world: one finished run with one decision point per headless attempt that reached a decision - a point is an attempt of `scope-review`, `build`, or `ship` materialized as the attempt's last recorded turn (`attempt["foreman"]`, which `record()` overwrites per try) when a foreman was consulted, the recorded transition when `model.decide()` chose and recorded one, or a reconstructed digest when neither survives (pre-foreman runs like `20260915-1915-aiplt-188`, whose attempts predate the transition field); scope attempts, cancelled attempts, and earlier tries of the same event are not points; the recorded decision for a `model.decide()` point is the transition action (`stage_passed`, `retry`, `exhausted`, `park`, `cancel`, from `decide()` in `runner/model.py`) in its own vocabulary, not one of `DECISION_ACTIONS`: carried as context for the labeller and never scored - the point itself stays scorable, its replay scored against the label; it is the recorded transition action that is never scored - while labels stay in `DECISION_ACTIONS`; the run's terminal status, retries, and tokens give each point its context, and pre-foreman runs count too, which lifts the corpus from 4 foreman runs with 29 valid decisions (5+10+8+6) to 6 finished runs with about 70 scorable points (local `~/.factory/runs`, 2026-09-17; 4+16+23+11+8+8 non-cancelled headless attempts, the cancelled-status two-ideas run contributing 23 because none of its attempts has outcome cancelled, and only 3 points hard-stop, all in `1322-2`; the other six runs are scoping, running, or without a headless attempt) ⚠ points inside one run are correlated, so splits happen by run, never by point
  ✗ one world per turn, independent - the current eval shape (`evals/foreman/cases/`); it drops what happened after the decision, which is what the label needs
  ✗ synthetic trees from re-runs of the same request - only two such pairs exist (`1037`/`1038` and `1006`/`1602`, identical request text; `1322`/`1322-2` carries different requests and shares only the plan name) and their worktrees diverged from attempt one

D-history-storage: Where do worlds live? (2026-09-17, factory-dream-loop/spec.md)
  ✓ ~/.factory/history: `~/.factory/history/{run-id}/` with `world.json`, `points/{id}/` snapshots, `labels.json`, `faults.json`, and the run's `outcomes.jsonl` and operator `note` copied into the world root with the same path rewriting as other copied content, built by `factory history build` from `runs/` and `archive/`, never committed; exports gain the `foreman/` tree minus `stdout.jsonl` and the attempt files a point snapshot reads (`stderr.log` joins the export list); an export preserves run-relative paths under `~/.factory/exports/{run-id}/` with a checksummed `manifest.json` (`export()` in `runner/outcomes.py`), so a bundle unpacked under `runs/` or `archive/` is a run directory to `factory history build`, and an exported run can become a world elsewhere - gate reasons and conditions carry repository content and even credential-shaped strings (run `1322-2`, condition C1), so a committed corpus needs a redactor the repo does not have ⚠ history is per machine, like runs
  ✗ commit worlds under `factory/evals/foreman/` - redaction risk; the five hand cases stay there as the labeller's check set
  ✗ build worlds inside each run directory - `factory gc` moves runs and `export` omits `foreman/`, so history would follow the run's lifecycle instead of the policy's

D-replay-fidelity: What does the replayed foreman get to read? (2026-09-17, factory-dream-loop/spec.md)
  ✓ snapshot at decision time: a digest snapshot taken at decision time, the files the event names (`gate.json`, `last-message.md`, `stderr.log`, the stage result file), and the plan directory as the attempt started with it (`attempts/{stage}-{n}/inputs/`), copied into a replay directory with every absolute path rewritten - that is what the skill tells the foreman to read; the runner writes the snapshot from now on, and history rebuilds it for older runs from `run.json` the way `capture.as_of` does, marked `snapshot: reconstructed`; a point whose attempt has no `inputs/` directory is built without `plan/`, keeps its digest and event files, stays scorable, and never crashes the build - runs from before `inputs/` was captured are the case today (`20260915-1915-aiplt-188`, done with 4 headless attempts, no `inputs/` in any of them, so all 4 of its points are reconstructed and planless) ⚠ a reconstructed snapshot drops the guidance the foreman wrote earlier in that run, and its `git` block reflects the worktree at capture time, not decision time
  ✗ digest and event only - what `evals/foreman/run.py` does today; it evaluates a blind foreman and tunes the skill for one
  ✗ a full worktree snapshot per point - runs are 0.4 to 1.3 GB on disk
  ✗ record and replay the live turn's tool calls - the live foreman runs `git` and `gh` freely; stubbing both is a project of its own

D-cold-vs-warm: Live turns after the first resume a Codex thread; the eval replays each point in a fresh session. Which is replayed? (2026-09-17, factory-dream-loop/spec.md)
  ✓ replay every point cold from its digest snapshot - the digest carries the last ten decisions, the accumulated guidance, and the open conditions, and live sessions restart often anyway (four restarts in twelve turns in the `1144` run, two in eight in `1319`) ⚠ a warm live turn also had its own earlier reasoning in context; each world point records its turn's origin (cold or warm, from the `cold` field of the `factory.foreman-turn` record in `runner/foreman.py`), auto points (`model.decide()` transitions) record no origin, and the report's per-origin agreement table covers foreman points with auto points listed separately, so the gap stays visible
  ✗ rebuild the transcript from `stdout.jsonl` - up to 1.3 MB per turn, unredacted, and Codex cannot resume a thread from a transcript file
  ✗ deploy cold-only turns to match the eval - Tobrun chose one long-lived session per run (user, 2026-09-17)

D-staleness: Runner code, gate codes, and the decision schema changed between recorded runs. How does history stay honest? (2026-09-17, factory-dream-loop/spec.md)
  ✓ identities recorded, relabel on schema change: each world records the runner revision, decision schema id, and skill hash it ran under; the labeller labels every point against the current protocol, so a point recorded under an old schema is labelled by what the current foreman should answer; `factory history label --relabel` regenerates model labels (never human ones) when `DECISION_SCHEMA` or the condition codes change; a recorded snapshot is never rebuilt, since it is the truth of what the foreman saw, and the digest builders are frozen for this slice (D-observation-builders) - the recorded situation stays real even when the recorded answer was forced by a bug since fixed ⚠ a recorded snapshot carries the digest format and gate codes of its day; the replay prompt says so, and the label is what the current foreman should answer to that observation
  ✗ expire worlds older than the last schema change - throws away the only history there is

D-point-exclusions: Which decision points are scored? (2026-09-17, factory-dream-loop/spec.md)
  ✓ hard stops unscored: every point except hard-stop ones, which stay in the world unscored - `enforce()` parks on `secret.found`, `action.destructive`, and a missing or tampered intent before reading the decision, so the answer changes nothing there; fallback points are scored, since the label says what a valid answer would have been; caps are not an exclusion because `caps_exhausted()` depends on the action the decision names, so the labeller reads the caps line and labels a cap-breaking action as rejected
  ✗ score everything - rewards nothing on hard stops and inflates agreement
  ✗ also exclude caps-exhausted points - not a property of the attempt; only some answers break a cap

D-policy-identity: How is a turn tied to the skill text that produced it? (2026-09-17, factory-dream-loop/spec.md)
  ✓ hash in turn record: every turn record gains `policy: {"skill", "references", "sha256"}` where `sha256` covers the generated skill file plus the generated `references/factory-run.md` it links, and the record schema becomes `factory.foreman-turn/2`; `_turn` resolves skill bundles on cold turns only and a warm turn's prompt is the event message alone (`runner/foreman.py`), so the policy paths for a warm turn are the session's cold-turn resolution, persisted in run state and reused for every warm turn of that session, and a session restart re-resolves, so one run can carry two policy hashes across a restart, which `factory report --by-policy` shows as two groups; `factory foreman <id>` prints it and `factory report --by-policy` groups intervention, override, and fallback rates by hash; a deploy writes both the source candidate hash and the resulting generated hash into its `decision.json` and commit body so a live hash maps back to its dream - the generated file differs from the source (the plugin build strips Claude-only frontmatter), and the protocol reference is half the policy the foreman reads ⚠ old records have no hash and report as `unknown`
  ✗ rely on `runtime.json` skills sha - that is per attempt and hashes the whole plugin tree, not the foreman skill

## Factory dream loop

D-counterfactual-scoring: The history is one chain per run, so a replayed decision that differs from the recorded one has no recorded outcome. How is such a decision scored? (2026-09-17, factory-dream-loop/spec.md)
  ✓ hindsight labels per decision point: an `accept` set, a `reject` set, and `allow_override` - the same shape as the five hand cases (`factory.foreman-eval/1`), so a replayed decision is scored by set membership without ever needing the unrecorded branch ⚠ this measures agreement with labels on a frozen set, not online value; the spec never claims more
  ✗ agreement with the recorded decision - imitates a foreman the user says is weak
  ✗ importance-weighted off-policy estimate - an LLM policy logs no action probabilities, so there are no propensities
  ✗ LLM judge at replay time - one paid judge call per policy version per point on top of the replay call; labels are judged once per point instead

D-labeller: Who writes the hindsight labels? (2026-09-17, factory-dream-loop/spec.md)
  ✓ LLM hindsight labeller with human veto: one fresh Codex session per finished run answering one `factory.hindsight/1` record (labels and faults together, through the host's single `-o` output and one output schema), and a person overrides a label with `factory history label --set`, which writes `label_source: human`; the runner splits the record into `labels.json` and `faults.json` - it sees the whole run after the fact through the world itself (the ordered attempt summaries and terminal status in `world.json`, the `outcomes.jsonl` and operator `note` copied into the world root, and every point's snapshot), which no single turn had; a human entry is never regenerated (user, 2026-09-17) ⚠ the labeller is itself a model with its own errors, and it sees the recorded action and the run's ending, which anchors it toward accepting what happened ⚠ a hand edit of `labels.json` that forgets `label_source: human` is regenerated on `--relabel`; the `--set` command exists so nobody edits the file by hand ? verify: on the five hand-labelled cases, matched to a world point by the digest's `run.created_at`, stage, and attempt, any action in exactly one of the model and hand `accept` sets, or a model accept the hand case rejects, is a disagreement; `check_hand_cases` also reports a case with no matching world point as unmatched, not skipped - `stale-plugin-scope-review-1`, whose digest's `run.created_at` matches the non-terminal scoping run `1006`, is one today - so all five cases are always accounted for; the report prints every disagreement and the mean accept-set size, and the hand label wins
  ✗ deterministic rules from what followed - "next attempt passed" says nothing about the cheaper action that was also available, and most interesting points are parks and overrides, where rules are silent
  ✗ hand labels only - the corpus then grows only when a person labels, which is the opposite of self-operating
  ✗ a different model for the labeller than the foreman - nothing shows a second model labels better, and it doubles the model surface; `hindsight_model` stays a config key so it can change without code

D-replay-score: How is one replayed policy version scored? (2026-09-17, factory-dream-loop/spec.md)
  ✓ ladder penalty: per point 1 minus 0.15 per ladder step above the cheapest accepted action when the action is accepted, else 0; a malformed decision or an override the label does not allow scores 0; per world: the mean over its scorable points; per policy: the mean over worlds, where a world whose every point is `scorable: false` is excluded from the mean and named in the report, mirroring how unlabelled worlds are excluded from scoring, and the deploy floor still counts worlds as written - the replay turn runs under the live foreman settings, `foreman_model` and `foreman_effort` from config (`runner/config.py`), so the incumbent's score is what the deployed policy scores under its own settings, which is why the replay cache key carries model and effort; the ladder (`regate`, `publish`, `advance` at 0; `wait`, `repair` at 1; `launch` at 2; `park`, `rescope`, `cancel` at 3) encodes the skill's own "cheapest sufficient step" principle, and equal weight per world stops one long run from dominating ⚠ weights are hand-picked constants in `runner/dream.py`, not learned ⚠ the labeller's accept sets bound the score: a wide set makes the cheapest action always right offline while it costs a wasted gate attempt online, which is why the labeller must justify each accepted action, the dream report prints the per-world mean accept-set size, and the hand-case check prints it for the check set
  ✗ run-level done rate - gameable: the gcp-costs run ended `done` with two overrides of a runner crash (`run.json` overrides, 2026-09-17)
  ✗ a token-cost term - tokens are spent by the stage agents, not the foreman; the ladder already charges an extra attempt

D-parallelism-bonus: Does the paper's parallelism term transfer? (2026-09-17, factory-dream-loop/spec.md)
  ✗ yes - a run has one worker and one attempt at a time (`executor.lock`, one slot per run)
  ⊘ not doing - reopen when the runner gains parallel attempts within one run

D-split-and-selection: How does the loop avoid picking a revision that only fits the runs it was tuned on? (2026-09-17, factory-dream-loop/spec.md)
  ✓ selection and confirmation split with margin 0.05: a repository is the run's normalized git remote URL, resolved at history-build time by running `git -C run.data["repo"] remote get-url` on the recorded remote name (`run.data["remote"]` stores the name, `origin` by `Run.create`'s default in `runner/model.py`, not the URL; `repo_slug()` in `runner/gates.py` resolves remote names to URLs the same way), normalized so the ssh and https forms of one repository are the same key (`git@github.com:acme/app.git` and `https://github.com/acme/app`), falling back to the normalized repository path when the worktree or its remote is unavailable, because today's runs carry five worktree paths for two remotes; split worlds by run into a selection set and a confirmation set; with three or more repositories, confirmation takes whole repositories that never appear in selection; with two, each repository contributes to both sets, split by run; a repository holding fewer than two worlds cannot contribute to both sets, so the split falls back to split-by-run across all worlds, the applied rule reported `split-by-run`, and the report names any repository that could not span both sets; the dream agent reads only selection-set traces; the incumbent skill stays in the candidate pool; the best candidate by selection score is then scored on confirmation with `--repeats` (default 2 there, 1 on selection) and deploys only when its mean beats the incumbent's mean by at least `max(dream_margin, 1 / scorable confirmation points)` - the incumbent in the pool guarantees no regression on the frozen set as scored, as in the paper; the margin floor of one point's worth absorbs a single flipped decision on a small set ⚠ the same confirmation set is compared again every dream round, so repeated rounds on unchanged history are repeated draws against it ⚠ a vanished worktree falls back to the normalized path and can fragment one repository across its checkouts; `split()` sorts worlds by run id before applying the repository rule and targets at least 6 confirmation worlds spanning 2 repositories when the corpus allows, falling back to split-by-run or a too-small corpus with the applied rule reported; with fewer than 2 worlds total or a `--worlds` filter yielding fewer than 2, confirmation is empty and confirmation scoring is skipped and the deploy is refused with reason `floor` and the report shows an empty confirmation table with no division by zero; when scorable confirmation points is 0 the margin floor is not computed and the margin gate cannot pass and `score_policy` over zero worlds is never computed; the confirmation-set hash is the sha256 over the sorted confirmation world ids, recorded in every dream's `decision.json`, and the report prints how many rounds the current confirmation set has served, counted as prior `decision.json` files under `~/.factory/dreams/` carrying an identical hash
  ✗ argmax over one pool - winner's curse on a corpus of a dozen runs
  ✗ K repeated replays per point with confidence intervals - multiplies paid calls; the margin plus `--repeats` (default 1) leaves this available without making it the default

D-dream-agent: What revises the skill, and where does its prompt live? (2026-09-17, factory-dream-loop/spec.md)
  ✓ Codex skill: a fresh Codex `exec` session per round under a new runner-only skill `factory/skills/dream/SKILL.md`, read-only sandbox plus one writable output directory, fed the current skill, the selection-set replay traces (event, decision, label, score, labeller note), and the prior rounds' scores; each candidate is staged as a full copy of the generated plugin tree under `dreams/{id}/candidates/{round}/plugins/factory/` with the candidate skill swapped in, so its relative reference links resolve and incumbent and candidate replay under the same layout - Codex is the unattended host (memory `prefers-llm-autonomy-over-guardrails`); a skill is the repository's unit for prompts, so `validate.sh` F03 and the length check cover it ⚠ the dream skill is itself prose the loop does not improve
  ✗ a Claude session - Claude is the interactive host in this setup
  ✗ a prompt string inside `runner/dream.py` - escapes F03 and the plugin build

D-dream-constraints: What stops a revision from memorizing the selection set or breaking the skill's contract? (2026-09-17, factory-dream-loop/spec.md)
  ✓ deterministic checks a candidate must pass before it is scored: frontmatter unchanged, every action of `DECISION_ACTIONS` still named in the decision table, at most 150 lines, no em dash, the F03 pattern absent, none of a denylist built from the selection worlds (run ids, repository paths and remotes, plan names, branch names, pull request numbers, the pattern of a run id, and every 40-character shingle of a recorded gate reason or last message), and a new credential-pattern scan shipped in the candidate checks (the repo has no reusable scanner; `secret.found` is a self-reported stage condition) clean - the scan matches credential-shaped literals in the candidate text (AWS keys, Slack tokens (`xoxb`/`xoxa`/`xoxp`), GitHub tokens, private key blocks) and rejects with `secret`, the families chosen from the credential shapes the recorded traces actually carry (run `1322-2` condition C1 holds both an AWS-shaped literal and a Slack token, the 28-character `xoxb` form slipping under the 40-character shingle length), the pattern list pinned as a module constant in `runner/dream.py` beside `LADDER` and `STEP_PENALTY`; the paper forbids copying trace-specific ids into policy logic; a check the loop cannot argue with beats a prose instruction (CLAUDE.md); the secret scan and the shingles exist because the revision is pushed to GitHub and was written from traces that carry repository content (D-history-storage) ⚠ the shingle rule also blocks a legitimate quote of a common gate reason; the dream skill says to paraphrase
  ✗ prose instruction in the dream skill only - models treat long rule lists as guidelines

D-fault-feed: How does the loop surface faults the foreman cannot fix? (2026-09-17, factory-dream-loop/spec.md)

  ✗ a separate paid classifier pass - same reading twice

D-fault-feed-consumer: Who acts on the fault feed? (2026-09-17, factory-dream-loop/spec.md)

  ⊘ not doing - a person reads the ranked list in the dream report; reopen when the same fault family tops the report in three consecutive dream rounds

D-budget: What bounds a dream round's spend? (2026-09-17, factory-dream-loop/spec.md)
  ✓ caps and cache: `--rounds` (default 3), `--repeats` (default 1 on selection, 2 on confirmation; an explicit `--repeats K` overrides both defaults, and K below 1 is rejected), `--max-calls` (default 1000) with replay results cached by policy hash, world id, point id, snapshot sha256, decision schema id, model, effort, and repeat ordinal under `~/.factory/dreams/cache/` shared across dreams - the repeat ordinal in the key is what makes `--repeats` more than a cache hit: the first pass at a point (ordinal 1) is cached and shared across dreams, repeats 2..K are always fresh calls, since a repeat is a draw, not a lookup, and without the ordinal the second repeat would be the cached first answer and would absorb no variance; a dream is roughly (rounds + 1) times the selection points plus 2 times 2 times the confirmation points, roughly 280 calls at today's about 70 scorable points, so the default cap of 1000 leaves roughly 3.5x headroom before rounds turn partial; a schema change in the key invalidates old answers instead of grading them under a new schema; the cache's policy hash is the policy hash per D-policy-identity - one sha256 over the staged tree's foreman skill plus the `references/factory-run.md` it links, the same combined hash the turn record and the deploy record carry - so a change to the protocol reference invalidates cached answers together with the skill, and snapshot sha256 is the sha256 over the raw stored bytes of the point's `digest.json` including `generated_at`, so a rebuilt snapshot with a new `generated_at` voids the cache by design; the dream id follows the run-id minting convention (`Run.create` in `runner/model.py`: a `%Y%m%d-%H%M` stamp plus a slug, a numeric suffix on collision) with the fixed slug `dream`, so ids read `20260918-1015-dream`; `factory history build`, `factory history label`, and `factory dream` alike take an exclusive non-blocking flock before any work - the `supervise.WorkerLock` idiom (a non-blocking flock file released on process death, `runner/supervise.py`) on a lock file under `~/.factory/` (`~/.factory/history.lock`) - guarding the whole history/dream surface, so no history command rewrites worlds or regenerates labels while a dream reads them, two concurrent dreams cannot race the cache or double-deploy, and any second concurrent invocation of the three exits with a message and does no work ⚠ the cache grows monotonically: entries are tiny replay answers, and a world rebuild changes the snapshot sha256 and orphans old entries naturally; pruning is out of scope this slice, reopen when `~/.factory/dreams/cache/` passes 1 GB
  ✗ uncapped - the paper's loop is free, this one is paid
